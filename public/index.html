Guide

      
How to run the factory, page by page. Updates are listed at the bottom under What's new.


      
Getting started

      
    
        
  1. Start a model server. Install LM Studio or Ollama. In LM Studio, open the Developer tab and start the server. Prefer a cloud model? Skip this and add a key on the Models page.
    2. 
        
  2. Pick a model. A coding model that fits your GPU's memory: 7–9B for 8–12 GB, up to 24B for 16 GB or a Mac with 32 GB+.
    3. 
        
  3. Write a work order in the cream ticket under the factory floor and press Ctrl+Enter.
    4. 
      

      


      
How the line works

      

        
StationWhat it does

        
PlannerTurns your goal into a short plan, reading workspace files and your Sources. Small talk gets an answer instead of a build.

        
BuilderWrites one file per work order. The draft is staged; your workspace isn't touched.

        
TesterChecks the draft in a throwaway copy: JavaScript syntax, JSON, Python syntax and your workspace's own npm test. It also fails a change to an existing file your goal never mentions.

        
ReviewerReads the diff and test results. It approves, or sends the work back with blocking issues. A failed test always means revise.

      

      
Work that's sent back returns to the Builder with the feedback attached, up to the number of attempts set in Settings (3 by default).


      
Writing good work orders

      
    
        
  • One file per line. "Create tools/rename.js that renames photos by EXIF date" beats "build me a photo app".
    • 
        
  • Name the file when you want an edit. The Tester blocks edits to files the goal doesn't mention, so the Builder can't wander.
    • 
        
  • Say what done looks like: inputs, outputs, flags and error messages.
    • 
        
  • Use blueprints. The chips above the ticket fill in a proven template: CLI tool, web page, Apify Actor project, PyTorch model, script or README.
    • 
        
  • Queue a night's work. One goal per line runs top to bottom.
    • 
      


      
Foreman: whole projects

      
Each work order builds one file. For anything bigger, write the whole project on the ticket ("a CLI that converts CSV to JSON, with tests and a README") and press ⚒ Foreman instead of Send.

      
    
        
  1. The Foreman plans up to 8 one-file work orders in build order: shared code first, then what uses it, then tests and docs.
    2. 
        
  2. Review the plan. Edit any order, remove ones you don't want, or add your own.
    3. 
        
  3. Pick the lines. The main line uses your Worker tuning; tick a LAN Foundry machine and choose its model to add a second line. Orders that don't depend on each other build at the same time, one per line.
    4. 
        
  4. Start project. The Foreman runs it on its own, even if you switch pages: every Builder sees the whole plan and the files built so far, so names and formats match.
    5. 
      

      
    
        
  • When an order fails every attempt, nothing else starts. The Foreman re-plans the remaining work around the problem (twice at most), or, if you chose Pause and ask me, waits for you to Retry, Skip or Stop. A model server that stops answering always pauses.
    • 
        
  • Final inspection. When every file is built, the Tester checks them together (syntax, imports and page links that point at missing files, your workspace's tests) and the Reviewer reads the whole project. Files with problems go back to their Builder with the notes.
    • 
        
  • One approval. Nothing touches your workspace until the project is done. Apply writes every file at once with backups; Undo puts them all back. With Auto-apply on, a project that passes inspection applies itself.
    • 
      

      
The Foreman plans with the Planner's model and inspects with the Reviewer's, so a stronger model there pays off. Projects show up in the left drawer with each file's progress; click a file to read it. A project that was running when the app closed comes back paused.


      
Approvals, Auto-apply and the queue

      
With Auto-apply off, every finished change waits in Staged changes. Click it to see the diff, then apply or reject. With it on, a change applies itself only when tests didn't fail and the Reviewer approved; everything else waits for you.

      
Every applied change keeps a backup of the file it replaced. Report on the ticket lists what happened to each goal, with two buttons:

      
    
        
  • Undo rolls an applied change back: the previous file returns, or a file the change created is removed. It refuses if you've edited the file since.
    • 
        
  • Retry puts a failed or staged goal back on the ticket so you can tweak it and send it again.
    • 
      

      
Stop (or Esc twice) ends the work order on the floor and moves on. If the app closes mid-queue, unfinished work orders come back paused: press Send to intake with an empty ticket to resume, or Clear to drop them.

      
Turn on Commit each applied change with git in Settings to get a commit per change when your workspace is a git repository.


      
Models and worker tuning

      
On the Models page, choose a provider (local, Claude, OpenAI, Gemini, OpenRouter or a custom OpenAI-compatible server), a default model and, optionally, a model per worker. Keys are encrypted with your system's keychain and never shown again.

      
Worker tuning

      
Each worker can override provider, model, temperature, top-p, max tokens and add standing instructions. Blank fields use the defaults.

      

        
SettingRule of thumb

        
Temperature0.1–0.3 for Builder and Reviewer (consistent code), 0.3–0.7 for the Planner. The presets set 0.2, 0.7 and 1.0.

        
Top-pLeave blank unless a model card recommends one. Ignored by OpenAI and Claude.

        
Max tokensRaise for long files (8192+). It must fit your model's context in LM Studio.

        
InstructionsHouse rules for one worker, e.g. "Node built-ins only" for the Builder.

      

      
A worker on a different provider than the default needs its model name typed in, because the dropdowns list only the default provider's models.


      
Skills

      
A skill is a folder with a SKILL.md: standing instructions that switch on when a trigger word appears in a goal, for the workers you choose. Starter skills cover house style, security review, READMEs, Node CLIs, Apify Actors and PyTorch.

      
---
name: House style
description: How I like my code.
triggers: [js, node]
roles: [builder, reviewer]
---
- Two-space indents and semicolons.
- Prefer small pure functions.


      
Sources and permissions

      
Sources are reference files and web pages the workers read while planning and building. Permissions in Settings decide what the AI may touch:

      
    
        
  • Read workspace files, run your tests, use Sources (on by default)
    • 
        
  • Internet: fetch pages linked in a goal (off by default)
    • 
        
  • Run Python scripts: the Run button in the training bay (off by default)
    • 
      


      
LAN Foundry: workers on other machines

      
    
        
  1. On the other computer, start a model server that listens on your network: in LM Studio, turn on Serve on Local Network in the Developer tab; for Ollama, start it with OLLAMA_HOST=0.0.0.0.
    2. 
        
  2. On the Models page, press Scan my network or add the machine by address, like http://192.168.1.20:1234.
    3. 
        
  3. In Worker tuning, set a worker's Runs on to that machine and type its model name. The console shows "Dispatching BUILDER on PC (LAN)" when it's used.
    4. 
      

      
Your code and prompts travel over your home network to that machine. Only add machines you control.


      
Watch

      
Watchers check a device or API on a timer while the app is open, chart the first value you track, and alert you when a rule trips.

      
    
        
  1. Pick a preset or Custom, fill in the address, and press Test connection to see the raw data.
    2. 
        
  2. List the values to track with dot paths: temp, bitcoin.usd, SUMMARY.0.MHS 5s.
    3. 
        
  3. Set a rule (above, below, equals, changes, or stops responding) and, if you like, a question for your model when it fires.
    4. 
        
  4. Optionally add a webhook: the alert is POSTed as JSON (watcher, message, values, plus text/content for chat apps). Point it at a smart plug's off URL, Home Assistant, a Discord webhook or ntfy.
    5. 
      

      

        
PresetConnects to

        
Antminer / cgminerTCP port 4028 with the summary command. Scrypt miners report MHS 5s; SHA-256 miners report GHS 5s. The miner's API must be enabled.

        
Bitaxe / AxeOShttp://<ip>/api/system/info: hashRate, temp, power

        
Ollama/api/ps, to know when your model server goes down

        
Crypto priceCoinGecko's free price API, every 5 minutes

      

      
Watchers, their chart history and alerts are saved. They poll while the app is open.


      
Training bay (PyTorch)

      
    
        
  1. Allow Run Python scripts in Settings > Permissions. If you use a virtualenv, put its python path in Python command.
    2. 
        
  2. Install PyTorch for your hardware (table below).
    3. 
        
  3. Send the PyTorch model blueprint with what the network should learn. Approve the files.
    4. 
        
  4. Open train.py in Workspace files and click Run. Lines like epoch 3 loss 0.41 draw the loss chart.
    5. 
      

      

        
HardwareInstall

        
Apple Siliconpip3 install torch (uses the GPU through MPS)

        
NVIDIAThe CUDA command from pytorch.org's install selector

        
AMD Radeon RX 7000 / 9000AMD's ROCm build of PyTorch (Windows or Linux). It reports as cuda, so scripts need no changes.

        
Other Windows GPUspip install torch-directml

        
No GPUpip install torch; keep models small

Troubleshooting

      

        
ProblemFix

        
"Model server unreachable"Start LM Studio's server (Developer tab) or Ollama, then click the model name in the top bar.

        
"The model took longer than..."Raise Model time limit in Settings > Generation, lower Max tokens, or use a smaller model.

        
Something odd happenedSettings > Open logs folder: server.log records every error with a timestamp.

        
Model error 400 or a context errorLower Max tokens, or raise the context length when loading the model in LM Studio.

        
The Reviewer keeps sending work backRead its issues in the Reviewer office. Make the goal more specific, give the Reviewer temperature 0.1, or use a larger model for it.

        
Python was not foundInstall Python 3, or set Python command to the full path of your python.

        
Mac says the app is damagedRun xattr -cr "/Applications/Freeze Foundry.app" once.

        
Windows SmartScreen warningMore info, then Run anyway. The installer isn't code-signed yet.

Ship

    
Turn what the factory builds into something people pay for.

    

        
1. Build an Apify Actor

        
Apify Actors are small automation tools (scrapers, data tools) that people rent on the Apify Store; Apify bills them and pays you a share. Click Apify Actor project above the work order on the Factory page, replace the description with what your Actor should do, and send it. The factory builds the four files an Actor needs in its own folder. Check the Actor ideas page for things people are asking for.

    

    

        
2. Publish it to your Apify account

        
Get your token

        

            
            
        

        

        
This creates (or updates) a private Actor and starts a build. Nothing is public until you choose to publish it in Apify.

    

    

        
3. Turn on earnings

        
In the Apify Console, open your Actor → Publication: write a clear README, set it public, then add monetization (pay per result or per event; Apify pays out about 80% of revenue minus platform costs). Test it on a few real inputs first; reviews and reliability drive sales. Expect small amounts at first. Most income comes from a few Actors that solve a specific, common problem well.
